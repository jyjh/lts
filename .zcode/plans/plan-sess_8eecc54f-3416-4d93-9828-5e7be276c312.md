## Fix 1 — AntiRollBar units documentation (trivial)

**File:** `src/+lts/+components/+Suspension/AntiRollBar.m`

The property comment for `stiffness` says "[N/m] at the bar end" but the wheel-rate formula `Kw = stiffness·MR²/leverArm²` (line 66) is only dimensionally correct for a **torsional rate [N·m/rad]**. The R26 values (1800) produce 24 kN/m only under the torsional interpretation; under the documented interpretation they'd give ~1.6 kN/m (6.8× too soft).

**Change:** Rewrite the `stiffness` property doc-comment (lines 20-25) to say it is the bar's torsional-equivalent rate [N·m/rad] referenced to the bar axis — the linear-equivalent end rate divided by leverArm. Add a dimensional note to the `getWheelRateStiffness` formula comment (line 66) confirming the units cancel correctly: `(N·m/rad)·(–)²/(m²) = N/m/rad` at the wheel. No code or value changes.

## Fix 2 — Tire relaxation state polluted by lateralStiffnessScale (small)

**Files:** `src/+lts/+components/+Tire/PacejkaTire.m`

The committed lagged slip state passes through `evaluationSlipAngle` (scale + clamp) before being stored, violating the documented "states remain in physical radians" invariant. When `lateralStiffnessScale ≠ 1` the relaxation recurrence mixes scaled and unscaled states, distorting the lag time constant. The evaluation-time scaling already happens at the MFeval input build sites, so the in-relaxation scaling is both wrong *and* a double-application.

**Changes (2 lines removed, 0 added):**

1. **`updateAllCorners` (line 565):** Delete `alpha = obj.evaluationSlipAngle(alpha);`. The MFeval-input build at line 584 (`alphaEval = obj.evaluationSlipAngle(alpha)`) already scales for force evaluation; the committed lagged state at line 575 will now stay in physical radians.

2. **`applyRelaxation` (line 714):** Delete `alpha = obj.evaluationSlipAngle(alpha);`. The caller `updateCorner` already applies `evaluationSlipAngle` at line 172 (`alphaEval = obj.evaluationSlipAngle(alpha)`) for the MFeval call.

**Test:** Add a case to `tests/TireContactTest.m` that sets `lateralStiffnessScale = 1.5`, runs two `updateCorner` advance calls with a known α step, and verifies the committed `cornerState.slipAngle` equals the unscaled relaxed value (not the scaled one). This locks the invariant for future correlation work.

## Fix 3 — Wheel-contact solve double-integrates ω (small, physics bug)

**Files:** `src/+lts/+simulation/Simulator.m`, `tests/SimulatorPhysicsRegressionTest.m`

`updateWheelDynamics` mutates `cornerState.angularVelocity` in-place, and the loop at `Simulator.m:213-254` calls it `nWheelIter` times per step with full `obj.dt` each time. At the default `wheelSolveIterations = 2`, wheel ω advances ~2·dt per 1 ms step (effective inertia halved). The fix snapshots ω at loop entry and resets each iteration so every pass is a fresh fixed-point attempt from the step-start value — matching the pattern already proven in `PacejkaTire.solveWheelContact`.

**Changes to `Simulator.step` (around line 213):**

1. Before the `for iter = 1:nWheelIter` loop, snapshot the four corner angular velocities into a local struct (e.g. `omegaStepStart`).

2. At the top of each iteration body, restore the four `cornerState.angularVelocity` values from `omegaStepStart` before calling `updateWheelDynamics`. This makes each iteration compute ω_candidate = ω₀ + dt·α(Fx(ω_prev_iter)), converging toward the semi-implicit solution instead of accumulating.

3. The differential re-solve (line 223-235), locked-diff overwrite, and powertrain update (line 241) remain inside the loop — they see the current iteration's candidate ω, which is correct for convergence. On the last iteration the converged candidate is committed (no further reset).

**New regression test** in `SimulatorPhysicsRegressionTest.m`:
- Build a minimal chassis-mode vehicle (reuse `directTorqueVehicle` helper), set `wheelSolveIterations = 2` (the default), apply a known drive torque, step once.
- Compute the expected Δω analytically: `Δω = dt · (T_drive - Fx(ω₀)·R) / I` using the Fx from the *initial* ω₀ evaluation (one explicit-Euler step).
- Assert `|ω_new - (ω₀ + Δω)|` is within tolerance. At `wheelSolveIterations = 1` the same assertion trivially holds (regression guard). The test must NOT set `wheelSolveIterations = 1` — that's the hole that let the bug through.

## Fix 5 — Derive chassis platform stiffness/damping from suspension (medium)

**Files:** `src/+lts/+components/+Chassis/SimpleChassis.m`, `src/+lts/+vehicle/VehicleConfig.m`, `src/+lts/+vehicle/VehicleManager.m`, `src/+lts/+vehicles/R26_base.m`, `src/+lts/+vehicles/R25.m`

Heave/pitch stiffness and all platform damping are hand-typed constants that must be hand-matched to what the corner springs/dampers produce. Roll stiffness is already correctly derived from the linked suspension (`getAxleRollStiffnessRad`); apply the same pattern to the remaining platform parameters, with a NaN-gated override matching the existing `rollStiffnessOverride`.

### 5a. Add derivation methods to `SimpleChassis`

New private methods that read the linked `SuspensionManager`'s per-corner `SimpleSuspension` units (front-left/rear-left are representative since front/rear corners share params):

- `deriveHeaveStiffness()`: `Σ(K_corner · MR²)` over 4 corners = `2·(K_F·MR_F² + K_R·MR_R²)`.
- `deriveHeaveDamping()`: `Σ(C_corner · MR²)` over 4 corners (use compression damping; rebound differs only in sign of velocity).
- `derivePitchStiffness()`: `K_F·MR_F²·frontArm² + K_R·MR_R²·rearArm²` (front + rear axle spring rates × CG-to-axle arm²).
- `derivePitchDamping()`: same form with damping coefficients.
- `deriveRollDamping()`: `(C_F·MR_F² + C_R·MR_R²) · trackWidth²/2` — mirror the roll-stiffness wheel-rate→roll-rate conversion already in `getAxleRollStiffnessRad`.

### 5b. Resolution logic in `updateFromAccelerations`

Before computing heave/pitch/roll moments, resolve each platform parameter:
```
K_heave_eff  = isnan(heaveStiffnessOverride)  ? deriveHeaveStiffness()  : heaveStiffnessOverride
C_heave_eff  = isnan(heaveDampingOverride)    ? deriveHeaveDamping()    : heaveDampingOverride
K_pitch_eff  = isnan(pitchStiffnessOverride)  ? derivePitchStiffness()  : pitchStiffnessOverride
C_pitch_eff  = isnan(pitchDampingOverride)    ? derivePitchDamping()    : pitchDampingOverride
C_roll_eff   = isnan(rollDampingOverride)     ? deriveRollDamping()     : rollDampingOverride
```
Use the `_eff` values in the moment/force equations (lines 153-216). The existing `KrollF/KrollR` derivation (from `getAxleRollStiffnessRad`) and the legacy `rollStiffness` fallback stay as-is.

Memoize the derived values on first call (run invariant, like `cachedSuspensionHasRollStiffness`).

### 5c. Config changes

- `VehicleConfig.m`: Add override fields to the `chassis` struct: `heaveStiffnessOverride = NaN`, `heaveDampingOverride = NaN`, `pitchStiffnessOverride = NaN`, `pitchDampingOverride = NaN`, `rollDampingOverride = NaN`. Keep the existing `heaveStiffness`/`pitchStiffness`/etc fields for backward-compat reading but mark them deprecated.
- `VehicleManager.fromConfig` (lines 239-246): set the new override fields from config. If the old fields are non-NaN, copy them into the overrides (preserves existing behavior for configs that haven't migrated).
- `R26_base.m` / `R25.m`: Change the chassis config to set the override fields to `NaN` (derive from suspension). Print the derived vs configured values at build time so the user sees the change.

### 5d. `torsionalRigidity = Inf` guard

In `SimpleChassis` constructor or `setSuspension`, error if `torsionalRigidity` is `Inf` with a clear message: "Use a large finite value (e.g. 1e6 N·m/rad) for near-rigid torsion; Inf is numerically unstable at dt=1ms with explicit Euler." R26's 162,518 is fine.

### 5e. Tests

- Add a test in `ChassisLoadTransferTest.m` that builds a vehicle with NaN overrides, links the suspension, and verifies the derived `heaveStiffness` matches `2·(K_F·MR_F² + K_R·MR_R²)` within tolerance.
- Add a test that a finite `heaveStiffnessOverride` is used directly instead of the derived value.
- Add a test that constructing `SimpleChassis` with `torsionalRigidity = Inf` errors.
